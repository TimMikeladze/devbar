# Local Dispatch System — Design Spec

## Overview

Add a dispatch system to the deloop local server that automatically (or manually) sends incoming annotation reports to Claude Code for processing. Reports arrive from the toolbar via `POST /api/reports`, get written to `~/.deloop/reports/`, and the dispatcher spawns `claude` CLI processes to handle them.

## Goals

- Dispatch annotation reports to Claude Code with zero manual config beyond running `deloop-local` in a project directory
- Support multiple projects sending to the same server, each with their own model/effort/concurrency settings
- Support both auto-dispatch (report arrives → Claude starts) and manual batch dispatch
- Use existing Claude Code subscription auth — no API key required
- Work with both Node.js and Bun, no runtime-specific APIs

## Non-Goals

- Toolbar changes (submit UX stays as-is: one button, all annotations bundled)
- Agent SDK integration (uses CLI spawning only)
- Persistent Claude sessions (each dispatch is a fresh `claude --print` invocation)
- Web dashboard or UI for monitoring tasks

## Architecture

Four modules, each with a single responsibility:

```
local.ts        → HTTP server (accepts reports, serves API)
local-cli.ts    → CLI entry point (start-or-register logic)
registry.ts     → Project registration + persistence
dispatcher.ts   → Queue, concurrency control, claude process spawning
```

### Data Flow

```
Toolbar POST /api/reports
  → local.ts writes report to ~/.deloop/reports/{timestamp}-{uuid}.json
  → if auto-dispatch enabled AND project is registered:
      → dispatcher.enqueue(reportPath, projectSlug)
      → dispatcher.process() pulls from queue, respects concurrency
      → spawns: claude --print --model X --effort Y --output-format stream-json -p "{prompt}"
         with cwd = project dir
      → writes result to ~/.deloop/results/{taskId}.json
```

## Module Designs

### 1. Registry (`registry.ts`)

In-memory map backed by `~/.deloop/projects.json`.

```typescript
type ProjectConfig = {
	slug: string; // derived from basename(cwd) or --name flag
	dir: string; // absolute path to project
	model: string; // "sonnet" | "opus" | "haiku" (default: "sonnet")
	effort: string; // "low" | "medium" | "high" | "max" (default: "medium")
	maxBudgetUsd?: number; // per-task cost cap
	concurrency: number; // max parallel agents for this project (default: 1)
	permissionMode: string; // "plan" | "default" | "auto" etc (default: "plan")
	autoDispatch: boolean; // whether reports auto-dispatch (default: true)
};

type Registry = {
	register(config: ProjectConfig): void; // adds/updates, persists to disk
	unregister(slug: string): void;
	get(slug: string): ProjectConfig | undefined;
	list(): ProjectConfig[];
};
```

- Loaded from `~/.deloop/projects.json` on server start
- Written to disk on every mutation (register/unregister)
- Survives server restarts

### 2. Dispatcher (`dispatcher.ts`)

Queue + concurrency-controlled process spawner.

```typescript
type Task = {
	id: string;
	reportPath: string;
	projectSlug: string;
	status: "queued" | "running" | "completed" | "failed";
	createdAt: number;
	startedAt?: number;
	completedAt?: number;
	result?: DispatchResult;
};

type DispatchResult = {
	taskId: string;
	exitCode: number;
	output: string;
	durationMs: number;
	model: string;
};

type Dispatcher = {
	enqueue(reportPath: string, projectSlug: string): string; // returns taskId
	dispatchAll(projectSlug?: string): string[]; // batch trigger
	getTasks(filter?: { status?: string; project?: string }): Task[];
	getTask(taskId: string): Task | undefined;
};
```

**Spawning:** Uses `node:child_process.spawn` to run:

```bash
claude --print \
  --model {config.model} \
  --effort {config.effort} \
  --max-budget-usd {config.maxBudgetUsd} \
  --permission-mode {config.permissionMode} \
  --output-format stream-json \
  -p "{payload.prompt}"
```

With `cwd` set to `config.dir`. The prompt is the `prompt` field from the `DeloopPayload` — this is the full markdown bug report generated by the toolbar's prompt template, containing all annotations, page context, console errors, etc.

**Dispatch tracking:** When a report is dispatched, its filename is recorded in the task. `POST /api/dispatch` (batch mode) scans `~/.deloop/reports/` for files not already associated with a task and enqueues them. This avoids double-dispatching without needing to move or rename report files.

**Concurrency:** Per-project. If `app-a` has `concurrency: 2`, up to 2 tasks run in parallel for `app-a`, independently of other projects. The dispatcher checks active count before pulling from the queue.

**Results:** Written to `~/.deloop/results/{taskId}.json` containing the full `DispatchResult`.

### 3. Server API (`local.ts`)

Existing endpoints unchanged. New endpoints added:

```
POST   /api/projects              Register a project
  body: ProjectConfig
  → 200 { ok: true, slug: string }

GET    /api/projects              List registered projects
  → 200 { projects: ProjectConfig[] }

DELETE /api/projects/:slug        Unregister a project
  → 200 { ok: true }

POST   /api/dispatch              Manual batch trigger
  body: { project?: string }      Optional: only dispatch for this project
  → 200 { tasks: string[] }       Array of taskIds

GET    /api/tasks                 List dispatch tasks
  query: ?status=running&project=app-a
  → 200 { tasks: Task[] }

GET    /api/tasks/:id             Get task detail + result
  → 200 { task: Task, result?: DispatchResult }
```

**Modified behavior for `POST /api/reports`:**

- Now reads `project` field from request body
- If `project` is set, the project is registered, and `autoDispatch` is true → calls `dispatcher.enqueue()`
- Reports without a `project` field still save to disk, just don't auto-dispatch

All new endpoints require bearer token auth (same as existing endpoints).

### 4. CLI (`local-cli.ts`)

Updated flags:

```
deloop-local [options]
  --port, -p          port (default: 3100)
  --host              host (default: 127.0.0.1)
  --token, -t         bearer token
  --name              project slug (default: basename of cwd)
  --model             model for this project (default: sonnet)
  --effort            effort level (default: medium)
  --concurrency       max parallel agents (default: 1)
  --max-budget        per-task cost cap in USD
  --permission-mode   permission mode (default: plan)
  --no-auto           disable auto-dispatch for this project
```

**Startup logic:**

```
1. Try GET http://localhost:{port}/health
2a. Server NOT running:
    - Start server (listen on port)
    - Register CWD as project via registry (in-process)
    - Stay alive
    - Print: "server started, project '{slug}' registered"

2b. Server IS running:
    - POST /api/projects to register CWD + config
    - Print: "project '{slug}' registered with existing server"
    - Exit 0
```

## Toolbar Integration

A new `project` prop is added to `DeloopProps`. The toolbar's `handleServerSubmit` includes it in the `POST /api/reports` request body alongside `payload`, `url`, and `title`:

```typescript
// DeloopProps addition
type DeloopProps = {
	// ... existing props
	project?: string; // project slug for dispatch routing
};

// In handleServerSubmit, the fetch body becomes:
body: JSON.stringify({
	payload,
	url: payload.url,
	title: payload.title,
	project, // new: included when set
});
```

## File Layout on Disk

```
~/.deloop/
  token                              # auth token (existing)
  projects.json                      # registered projects + config
  reports/                           # incoming report payloads (existing)
    {timestamp}-{uuid}.json
  results/                           # dispatch results
    {taskId}.json
```

## Dependencies

None new. Uses:

- `node:child_process` — spawning `claude` CLI
- `node:http`, `node:fs`, `node:path`, `node:os`, `node:crypto` — already used

## Example Usage

```bash
# Terminal 1: start server + register app-a with opus
cd ~/workspace/app-a
deloop-local --model opus --effort high --concurrency 2

# Terminal 2: register app-b with haiku, exits immediately
cd ~/workspace/app-b
deloop-local --model haiku --effort low

# In app-a's code:
# <Deloop server="http://localhost:3100" token="..." project="app-a" />

# Manual batch dispatch via curl:
curl -X POST http://localhost:3100/api/dispatch \
  -H "Authorization: Bearer $(cat ~/.deloop/token)" \
  -H "Content-Type: application/json" \
  -d '{"project": "app-a"}'

# Check task status:
curl -H "Authorization: Bearer $(cat ~/.deloop/token)" \
  http://localhost:3100/api/tasks?project=app-a
```
